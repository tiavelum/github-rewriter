# Replay a repository

These steps take a replay from the owner's first answers to the replay holding the source's name. The commands, the options and what each script prints are in `replay/README.md` of tiavelum/github-rewriter; read it from `main` before the first step, and take each command from the part these steps name.

## Roles

- You survey the source, write the mailmap and the types file, plan, read every output, check the result and record the run.
- The owner creates the target and changes its settings, runs the replay, deletes branches, and archives and renames repositories. Give each of these steps as one command block, since a Claude session's access to GitHub refuses them.
- Have the owner run `run-replay.py` on their own machine with their own `gh`, since a Claude session's access to GitHub appends a "Generated by Claude Code" footer to every body it creates without one, and the replay copies the source's bodies.
- Leave every git step over SSH to the owner's machine; a Claude session has no SSH.

## The run's issue

Open an issue in tiavelum/github-rewriter titled `Run: replay <source> into <target>` as soon as the owner names the source. Keep in its description the owner's answers, the types table and the options of the run, so that a new session can resume from the issue alone. Keep the mailmap out of it and out of the repository; describe its lines by the identities they map, without the addresses the owner keeps private.

## Ask the owner

Ask these before planning, each with your recommendation, and record each answer on the run's issue.

1. **Replay or rewrite**: replay into a new repository, or rewrite the identities in place. Recommend the replay for the reasons of `docs/decisions/0001-replay-into-a-new-repository.md`. For a rewrite, follow `rewrite/README.md` instead of these steps.
2. **Identities**: list every identity of the source as author and as committer, with the commands under "Survey the source", and ask which are the owner's, what becomes of `GitHub <noreply@github.com>` as the committer of changes made on github.com, of Claude as a committer, and of any test identity.
3. **Merge commits**: replayed as squash merges, the default, or kept with `--keep-merges`.
4. **Types**: titles typed, the default, or kept with `--no-types`; with types, the owner confirms the types table and the squash summaries of "Plan".
5. **Signing**: whether the owner's recreated commits are signed with `--sign`, with the requirements "Running a replay" names.
6. **Names**: the target's name, and the name the replay takes over at the end, for `--final-name`.
7. **Trial**: recommend a trial into a throwaway private repository first where the run uses an option, or the source a feature such as merge commits into other branches, that no earlier run's issue in tiavelum/github-rewriter records.

## Survey the source

Have a mirror made as "Planning a replay" shows, then count the identities in it:

```sh
git -C "$mirror" log --all --format='%an <%ae>' | sort | uniq -c | sort -rn
git -C "$mirror" log --all --format='%cn <%ce>' | sort | uniq -c | sort -rn
```

Show them to the owner as a table of identities with their counts as author and as committer, and write the mailmap from the answers, as "Planning a replay" describes.

## Plan

1. Plan once with the mailmap, as "Planning a replay" shows, and read every line it prints.
2. For each title it changed with `guessed`, and for each commit pushed directly to the default branch, propose a type from the commit's subject and the files it changes.
3. Read each squash message it wrote for a pull request merged with a merge commit against that pull request, and propose a `summary` line where the summary misses what the pull request did.
4. Show the owner the types and summaries as one table of hash or number, type or summary, and subject; write the confirmed ones into the types file and plan again into a new event file.
5. Repeat until the owner confirms the output and it reports no guessed types, unless the owner accepts the guesses that remain.

Where this session cannot read the source, give the owner the planning commands to run and read the output they paste.

## Run

1. Have the owner create the target and set it up as "Running a replay" says, with the settings it names.
2. Give the owner one command block that writes the mailmap and the types file on their machine, makes the mirror, plans, and runs the replay with the options the owner chose. Have them compare the totals the plan prints with those of your last plan, and stop where they differ.
3. Ask the owner to keep the machine awake until the run prints the target's URL.
4. When the run stops, ask for its last lines, find the cause as "Stopping and resuming" says, and have the owner run the same command again once it is removed.

## Check

1. Compare the target with the source yourself, read-only:
   a. Every item under its number, with its kind, title as planned, state and state reason, labels and merged state; every label with its colour and description.
   b. Every body and comment equal to the source's, except where a hash of a recreated commit was replaced, and without a footer the source lacks.
   c. The default branch: as many first-parent commits as the source's, each tree equal to the tree at the same step of the source, every subject typed, and authors and committers as the mailmap and "What the target ends with" give them.
   d. The branches: those of the source, and those "What the target ends with" says stay.
2. Record the result on the run's issue.
3. Have a `checker` agent that did not see the run check the same points against the source and the event file. Name in its brief the addresses the target may hold, and have it report any other address only by where and how often it occurs, masked, since a checker tends to name the private values it finds.
4. List for the owner what a Claude session cannot read and the owner checks before archiving: the source's secrets, variables, webhooks, deploy keys and collaborators.

## Take over the name

1. Have the owner take over the source's name as "Taking over the source's name" says: sub-issue links first, then archiving and renaming, then the settings and the local clones.
2. Record each step on the run's issue as the owner reports it, and close the issue once the last one is done.
3. Remind the owner to delete the state file and the work repository next to the event file once the replay is checked.
